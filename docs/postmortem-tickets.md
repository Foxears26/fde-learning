## 教训一：分类准确率测不出 RAG 效果

最初用分类准确率对比有 RAG / 无 RAG，两边都是 100%。该指标能检查分类器，
却不能回答“检索是否改善建议回复”。如果据此判定 RAG 无效或有效，结论都会缺少证据。

根因是指标没有对齐要评估的行为：`process_ticket` 先调用模型分类，再决定技术类是否
检索 FAQ；检索结果只进入后续回复 prompt。RAG 没有参与分类，分类准确率自然不能
测出它对回复的贡献。两种模式各自调用分类器，未来即使出现分类差异，也可能来自模型波动。

已补充 `expected_citations`、`expected_key_points`，按同一批 10 条工单统计：

| 指标 | 有 RAG | 无 RAG |
| --- | --- | --- |
| 分类准确率（分类在检索前完成，与 RAG 无关） | 100% | 100% |
| 引用准确率 | 75% | 0% |
| 关键信息覆盖率 | 85% | 75% |

引用准确率以期望分类为 technical 的工单为分母，命中至少一个期望 FAQ 即算该工单命中；
关键信息覆盖率按全部期望信息点加权，检查建议回复的忽略大小写子串匹配。失败工单保留在
分母里。计算逻辑用 mock 回复测试，不依赖真实 LLM 的稳定性。

记录中 T07（创建返回 422）两种模式的回复质量得分均为 0，疑为知识库缺口或期望答案
问题，根因待查。FAQ-6 / FAQ-7 已写出 `info / warning / critical`，应先保存该工单
实际检索的 top-3、回复及期望字段，检查是否检索漏召回、引用了另一条等价 FAQ、
回复措辞未匹配规则，或模型没有回答。不能先把 0 分定性为知识库缺失。

后续评估先明确目标行为，再选指标：分类看分类准确率；引用看来源命中与人工支持性检查；
内容看信息点覆盖及正确性。保留逐条结果、模型、代码版本和期望答案，才能解释分数变化。
本轮数字只来自 10 条工单，规则命中也不证明回答正确、完整或引用充分。

## 教训二：旧镜像返回 404，宿主机改代码不会更新容器

项目记录中的现象是：代码已经有 `/tickets`，容器访问却返回 404。影响是新接口在该
运行实例中不可用；仅查看宿主机路由文件容易误判为路由挂载问题。

根因是运行了旧镜像。当前 Dockerfile 使用 `COPY fastapi/ ./fastapi/`，构建时把代码
放进镜像，运行命令没有挂载源码目录。镜像保存构建时的代码快照；宿主机文件改变后，
已有镜像和容器不会自动更新。`docker restart` 重启旧容器，`docker start` 启动旧容器，
都不会执行 Dockerfile，也不会换成新构建的镜像。

排查顺序：先确认请求的主机端口和进程，再查看 `/openapi.json` 是否含 `/tickets`；
对容器使用 `docker inspect --format '{{.Image}}' alert-api` 查看其镜像 ID，
与 `docker image inspect --format '{{.Id}}' alert-api:project2` 比较。
如果 tag 指向新镜像而容器 ID 仍旧，也说明只 build 没有替换容器。

修复流程是从仓库根目录重新 build，然后停止、移除旧应用容器，再以新镜像创建容器。
完整命令见 [runbook](runbook.md#docker-启动)。重建保留 FAQ 缓存命名卷，key 始终通过
`--env-file .env` 在运行时注入，不通过把 `.env` 复制进镜像来修复配置问题。

重新部署后先检查 `/hello` 和 OpenAPI，再发送一条非技术和一条技术工单，检查 HTTP 状态、
返回字段及引用。OpenAPI 有路由只能证明接口已发布，不能代替模型和检索路径的验证。

Docker 的镜像层创建后不可变，具体机制见
[官方镜像层说明](https://docs.docker.com/get-started/docker-concepts/building-images/understanding-image-layers/)。
